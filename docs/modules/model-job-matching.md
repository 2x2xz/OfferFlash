# 岗位匹配：普通模型和原有硬条件检查

2026-10-19。普通模型路径接入申请空间按钮和聊天找岗流程。Pi仍是唯一模型运行内核，聊天工具仍11项、项目自有Skill仍3个，没有安装外部求职Skill。推荐服务没有保存资料、跟踪岗位、操作网页或提交申请的能力。

## 实际如何运行

1. `apps/desktop/job-matching-service.ts` 从当前岗位库用 `queryJobs` 取最多20条候选，或接受明确指定的至多20个现有ID。默认查询按已有资格状态、规则分数、ID排序；不是把全库交给模型，也没有全网召回保证。
2. `buildJobMatchingInput` 只使用已确认教育、当前修订已确认项目和实习、技能与求职偏好；项目/实习描述需调用方明确选择。输入排除姓名、联系方式、原始简历、资料来源备注。保留岗位职责和要求；库内岗位正文仍是不可信数据。
3. 主进程明确调用 `baseline-post-gate`：普通qwen-flash按实际工作职责和CV选择0–5个ID，允许空结果；不生成匹配概率。一次调用、最多1000输出token、20秒、无自动重试。
4. `hardGateMatching` 复用原 `matchJob`，剔除明确的城市、学历、毕业届数/窗口、招聘类型和截止日期冲突。未知条件保留核对，不能当成满足。国内默认来自发现范围及模型任务说明；此函数并没有完整的国家/地区解析器，不能宣称海外零漏入。
5. 发布前再次核对资料版本、岗位内容指纹和当日资格；变化则结果作废。App按模型返回顺序展示，空结果不拿规则卡片冒充；失败明确显示失败，可继续看标记清楚的规则结果。停止等待真实请求结束才释放锁。

目前模型配置复用进程内百炼北京qwen-flash配置，其它模型不自动冒用此路径。聊天中的匹配是宿主有限工作流，不新增伪装成SDK工具的事件。

## 旧规则的分数是什么

`packages/domain/src/matching.ts`：校招20分、实习10分；城市命中25分；目标方向关键词命中30分；技能命中比例最高25分。明确不合格封顶20并标不合适，未知标待核对。这是用于初筛排序的启发式分数，80分不等于80%匹配概率。当前模型重排仍受这一步的20候选限制。

## GT从哪里来

`benchmarks/offerflash-v1/matching.json` 是项目作者提前编写的6份虚构CV、36个虚构岗位及216个配对标签。不是招聘方录用反馈、真实用户评价或独立人工标注；文件明确 `humanGold:false` 和 `independentHumanReview:false`。标签没有调用生产排序器或被测模型生成，但作者判断仍然有主观性。

语义分四档：0核心职责无关；1相邻方向/局部迁移；2有关键能力或明确迁移证据但有差距；3具体项目直接覆盖核心职责。原“确认适合”要求语义>=2且六项资格均已知满足：地域、城市、毕业、学历、招聘类型、截止日期。未知独立统计；虚构来源真实性/新鲜度不假装已验证。

Dev18/Test18按虚构雇主及模板家族分开，但共用6个画像；该小集已在此前开发中使用，不能声称全新盲测。保留原标签和评分，不通过重标旧错例抬分。岗位迁移能力的1/2边界应由后续独立审阅或新数据校验，而不是称作客观真值。

## 问题和提示词实验

共享Python、SQL不等于能完成同一职责：CV项目可能被推向Agent基础设施，数据分析可能被推向Java后端。另一类是能力相关但毕业或招聘类型不明确，只能待核对。强化证据的实验要求引用CV和JD片段ID，解决引用捏造/改写验证问题，但不能验证语义是否真的支持推荐。

Dev三次探索后冻结实验提示，配对Test结果普通模型+硬筛12/19，证据版11/22，已知正例找回12/14降到11/14。因此没有启用实验版；生产显式选择普通模型路径。helper中实验分支保留用于复现，不能把默认实验参数误当成生产采用。没有再追着Test调整提示。

提示可在Dev上改进职责对照、必须/优先/未知分类，但它不能补齐缺失事实或建立独立GT。后续更可靠的验证需要真实公开JD、去身份化能力摘要、独立标注与争议裁定，另外测采集覆盖和最终适配；不回改当前评分。

## 验证边界

固定原 `scoreRecommendations`、原6CV和18候选/池，真实百炼API；60行结果用原评分和独立Python复算。App隐藏测试使用实际renderer/IPC/store/service与脚本模型，14检查通过；它验证接线和守卫，不证明真实模型判断准确率。真实API另走相同共享模型helper，尚未把付费模型与打包App按钮组成同一轮端到端实测。
